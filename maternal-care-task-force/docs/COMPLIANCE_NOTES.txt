MCTF MEMBER SITE — COMPLIANCE NOTES
Prepared for the Task Force co-chairs and county health department privacy officers
2026-09-03

1. PHI TOUCHED AND WHERE IT FLOWS
   Intended: NONE. The system stores governance content, public program
   listings, aggregate county statistics, professional member identities,
   and de-identified barrier categories.
   Personal data (not PHI) that is stored: member names, organizations,
   roles; member email/phone only with opt-in; reporter email on form rows
   (verified by Google, never served to the site).
   Flow: Google Forms -> content Sheet (admin-owned) -> Apps Script web app
   (execute as admin) -> browser -> Google Sites iframe. No third party
   receives any data. No analytics, tag manager, or pixel is included.

2. CONTROLS APPLIED
   - Authorization: web app is read-only. Every entry point runs
     authorizeRead_ then an audit write, then work (Api.gs). Admin functions
     run requireAdmin_ (Auth.gs) against a Script Properties allowlist.
   - Publication gate: only rows with Published = TRUE leave the sheet.
     Form free-text is served only after a co-chair marks it Published.
   - Contact consent gate: member Email/Phone served only if ShareContact.
   - Data access: all Sheets I/O in DataAccess.gs via openById under the
     service identity; never getActiveSpreadsheet.
   - Audit: separate spreadsheet, separate folder, six-year retention;
     entries hold actor, role, action, resource, outcome, session; no content.
   - Output encoding: all sheet text is HTML-escaped client-side; links are
     rendered only for http(s) URLs.
   - No secrets in code; IDs in Script Properties.
   - Barrier form: month-only date, closed-choice categories, 500-char text,
     explicit prohibition of identifiers on the form and on the site.

4. REGULATORY REQUIREMENTS IMPLICATED
   - HIPAA Privacy Rule minimum necessary; de-identification standard
     (164.514) as the bar for anything narrative on the site.
   - HIPAA Security Rule audit controls and six-year documentation
     retention (164.312(b), 164.316(b)(2)(i)) applied by policy even though
     no ePHI is expected.
   - Maryland PIPA: member emails/phones are personal information; opt-in
     and minimal storage applied.
   - Neutrality: the site is a Task Force tool, not a marketing channel for
     any member organization. Member listings state professional role only;
     no member organization's services are described, ranked, or promoted;
     resource rows are added only through the same review as every other
     row. Task Force participation is separate from any member's business
     interests, and the site must not be used to advance them.

5. RESIDUAL RISK
   - Admin error publishing identifying text. Mitigation: review columns on
     form tabs; periodic spot-check by Privacy Officer; footer reminder.
   - URL leakage of the web app outside Sites sharing. Mitigation: content
     is public-safe by design; rotate deployment if needed.
   - Sheets has no row-level security; anyone with sheet Editor access sees
     reporter emails. Mitigation: Editor access limited to named admins.

6. OPEN QUESTIONS FOR THE TASK FORCE
   a. Which Google identities will members use (county Workspace, hospital,
      personal Gmail)? This decides "Anyone with Google account" vs "Anyone".
   b. Who are the named admins with Editor access to the content sheet?
   c. Who reviews BarrierLog submissions and on what cadence?
   d. Should member contact details be shown at all, or should the site
      point to the co-chairs as the single contact?
   e. Does the Task Force want the site to be public-facing for families
      later? That is a different product (public resource page) and should
      not share this sheet.
